解鎖門檻設計（累積押注金額）
翻牌機制：累積押注每跨過一個門檻，玩家就獲得 1 次「翻牌機會」（非解鎖固定位置的格子）。玩家可用累積的翻牌次數，自由翻開任意一個尚未翻開的格子——可翻次數 = 已解鎖次數 − 已翻開數。沒有剩餘次數時，所有未開格顯示鎖頭、不可點擊。
為何不影響經濟：集滿當日總門檻後可翻次數累積至 9，玩家最終仍會翻完全部 9 格、拿到全部獎項；翻牌結果依機率表權重於當日解鎖時決定並寫死，玩家翻開順序不影響已定結果，RTP 與通膨風險不變。
為什麼改用累積押注金額而非 Spin 次數？
Spin 次數對不同押注段的玩家體驗差異極大——低押注玩家每次 ₱1，高押注玩家每次 ₱100，同樣的 Spin 數對後者幾乎沒有成本感。
改用押注金額後，大 R 玩家可因高押注段快速過關，機制對各押注段玩家更為公平且有感。
⚠ 本章所有門檻與獎項金額皆為「示範用範例值」，不是實際上線值：下表與全文出現的 ₱100／₱3,650／₱1／₱3／₱8／₱18 等數字，僅用來說明機制如何運作。
實際的累積門檻與各階獎項金額，一律由營運在後台「模板」中設定，並依玩家命中的標籤規則套用不同模板——同一檔活動的不同標籤族群，會拿到不同的門檻數列與不同的獎項金額。
開發請把門檻與獎項金額一律視為「由模板讀入的變數」，不得將任何數值寫死在程式或前端（模板規格見 DEV §06 模板管理，標籤對應見 DEV §12）。
累積門檻的計算方式（累積制，對齊 DEV §03／DEV §06 模板）：模板提供一組 9 個累積押注門檻（各貨幣各自一套）。內部 today_wager 持續累加，取得第 d 次翻牌機會的條件為 today_wager ≥ 累積門檻[d]；「本階段所需」＝相鄰累積差；總門檻＝第 9 個累積門檻。
下表以 [100, 220, 360, 550, 850, 1250, 1700, 2500, 3650] 為示範數列（總門檻 ₱3,650）說明推算方式，實際值以模板設定為準。

UI 顯示原則：玩家畫面只顯示「再押 ₱X 解鎖下一次機會」（X = 下一累積門檻 − today_wager），進度條呈現「本階段進度」；永遠不顯示總門檻，讓玩家覺得每階段都好達成（詳見 DEV §05 UI）。
幣值維度（2026-06-26 開案 · C3）：每套幣值（如泰銖 THB）獨立設定對應的解鎖門檻、獎池與規則——不同幣值不是匯率換算，而是各自一套配方（門檻數列、9 格獎池金額、RTP 區間皆獨立）。後台活動設定以「幣值」為一個設定維度（見 DEV §03 資料結構 / DEV §06 後台），同一活動概念可依幣值各開一組設定。
（2026-06-26 對齊後台原型）以上門檻、獎池、RTP 皆為單一貨幣的設定；一檔活動可配置多貨幣，各貨幣獨立設定、RTP 各自驗算（後台以 currency tabs 切換，見 DEV §06 多貨幣設定）。

重置規則
🕛
每日 reset（固定 24 小時週期）
每日 reset 為固定 24 小時週期：當日累積押注（today_wager）清零，獎項組合重新產生並重新洗牌。最終獎位置每日動態隨機，不再固定於特定格
（2026-06-26 開案）活動「總週期」另依活動設定（如兩週）
⏸️
當日未翻完不補
今日已賺取但未使用的翻牌次數、未翻開的格子，隔日一律清零。不保留進度——製造急迫感驅動玩家當日完成
🎲
動態洗牌分配
每日開始時執行洗牌，小獎×5、中獎×2、大獎×1、最終獎×1 隨機分配到 9 格（格數組成固定，各階金額由模板設定）。玩家看到攤開結果後點「開始遊戲」才執行洗牌，格子翻回背面。
重置週期與時間點（2026-06-26 開案）：
① 固定 24 小時週期（C1）：每日 reset 為固定 24 小時循環；活動「總週期」則依各活動設定（例：兩週檔期），到期即整檔結束（搭配 DEV §05 活動期間元件呈現）。
② Reset 時間點可逐活動設定（C2）：不同活動 ID 可各自設定 reset 時間點（非全站統一），以 Server +8 為基準。例如 A 活動 00:00 reset、B 活動 06:00 reset，互不影響。
＊全系統一律以 UTC+8 設定與計算；不做「依各線路時區調整 reset 時間」（見 DEV §13 二、時區處理）。
（2026-06-26 對齊後台原型）每日 reset 為固定 24h 週期；reset 時間點可依活動（campaign）各自設定、以 Server UTC+8 為準、精確至秒。後台「基本資料」新增「每日重置時間」欄位（admin_daily_reset_time），一番賞累積門檻即於該時間點每日歸零（見 DEV §06 表單）。
玩家路徑分析
動態洗牌＋自由翻格：最終獎位置每日隨機洗牌且面朝下，玩家不知落點。由於翻牌次數可用於任一未開格，最終獎不再綁定特定門檻位置——玩家有機會在前段就翻中，也可能留到最後；要拿到最終獎，前提仍是累積足夠押注換到該次翻牌機會（最多 9 次＝集滿該模板總門檻）。此設計兼顧每日新鮮感、公平性與「自選挖寶」的期待感。
版型主題僅影響視覺呈現：版型主題僅影響視覺呈現，核心循環與數值不受影響；iFrame 依 campaign.theme_id 載入對應 asset bundle，可熱更新、不需重出遊戲版本。換主題只替換 icon／背景／9 格美術／開獎演出／文案／主色，門檻、9 格獎池、第幾抽權重、RTP 與後端邏輯一律不變（詳見 DEV §04 技術架構、DEV §06 主題資產對應規範）。

技術機制
後台發卡時設定允許使用的遊戲清單與局數。玩家使用時，系統須能讓玩家直接進入指定遊戲並自動套用該卡（跳轉手段由開發與集成商議定）
亂數模型（固定池 ＋ 不放回加權抽）
獎池組成固定、金額由模板決定：每日獎池固定為 9 格＝小 ×5、中 ×2、大 ×1、最終 ×1（格數組成不可變）；四階的金額由該玩家命中的模板提供，因此不同標籤族群的當日獎池總額不同。當日獎池一經產生即不可變動。

產生方式：玩家每日首次解鎖時，依標籤規則命中的模板權重以不放回加權抽產生 9 格排列並寫死當日 DB，當日不可重抽。翻完 9 格必得該模板獎池的全額，完成者 RTP 由該模板的獎池總額與總門檻共同決定、零變異、絕不超池。

終獎位置有機化：終獎不固定第 9 格，由權重分佈於後段（各模板分佈不同，見下方示範表），避免每日回訪玩家看破。
後端 RTP 驗算公式（每貨幣 × 每模板各自驗算）
模板 RTP = ( 該模板 9 格獎項金額總和 ) ÷ ( 該模板第 9 格累積門檻 )

分子＝該模板四階獎項按格數加總（小×5 ＋ 中×2 ＋ 大×1 ＋ 最終×1）；分母＝該模板的總（累積）門檻。兩者皆為模板設定值，隨標籤族群而異，公式中不含任何固定金額。
每套貨幣（各貨幣一套）× 每個模板各自代入、各自驗算，不做匯率換算。後台即時試算，超出該模板目標 RTP ±0.1% 即警示、擋送審。
分眾架構：標籤規則（AND 複合條件）→ 模板（對齊後台原型 v2）
對齊後台原型 v2：分眾以「標籤規則 → 模板」映射列表表達；標籤僅用於選模板，未命中任何規則走預設配置、活動照常可玩（無准入閘門）。完整規則見 DEV §12 玩家標籤與權限規則。

① 模板（給什麼）＝CRM 維護：每個模板含 門檻表(9格)＋權重表(9×4)＋目標RTP（＋押注比例／貨幣／版本）。模板為獨立實體，可被多檔活動與多條標籤規則共用（見 DEV §06 模板管理）。
② 標籤（給誰）＝DA／CDP 提供：玩家分群標籤由 DA 打上（大客／中客／小客／高風險／低風險），box／CRM 不自算、只比對。
③ 標籤規則（AND 複合條件）：每列規則＝多個標籤 chip（AND，需同時符合）→ 指定一個模板（例：大客 AND 非高風險 → 忠誠加碼）。單一標籤不足以命中，須整組條件同時成立。
④ 預設配置（固定置底、不可刪除）：未命中任何規則 → 走預設配置對應的模板，活動照常可玩；標籤僅用於選模板，未命中不會使活動消失。
⑤ 即時衝突檢查：標籤組合重複、或規則未選任何標籤 → 紅底警示、擋送審。

照顧的兩個槓桿（寫在模板的「意圖」裡）：(1) 目標RTP 越高→總門檻越低；(2) 終獎最早格越前→早退也可能已中終獎。系統可由「意圖(目標RTP＋終獎最早格)」自動編譯出門檻＋權重表。以下為 PHP 示範（各貨幣各自一套、結構相同）。

04 系統行為需求 SYSTEM BEHAVIOUR REQUIREMENTS
本章寫法：只列「系統必須達到的結果」與「不可違反的約束」。資料表結構、介面端點、傳輸欄位、佇列拓撲等實作手段由開發自行決定，只要行為與驗收標準成立即可。數值規則見 DEV §02／DEV §03，標籤匹配規則見 DEV §12。
一、押注累積行為
需求要達到的結果
近即時累計玩家每次押注後，其當日累積押注金額須近即時反映到活動進度上——玩家在遊戲內完成一次押注後回到寶箱面板，看到的進度應已包含該筆押注，不得等到下次登入或隔日批次才更新。
計入範圍只累計玩家所在線路落在該活動投放線路內的押注；線路不在清單內的押注不計入且玩家無感（不顯示活動、不報錯）。
擇一原則玩家同一時間只會進行 1 檔抽寶箱活動；其餘符合的活動不顯示、押注不計入。
跨門檻即得次數累積金額每跨過一個門檻即取得 1 次翻牌機會；可翻次數＝已解鎖次數 − 已翻開格數。單筆押注一次跨過多個門檻時，須一次補足對應的多次機會，不可只給 1 次。
次數不逾日當日未使用完的翻牌次數不累積至隔日，隨每日重置一併清除。
二、每日配置解析與鎖定
需求要達到的結果
何時決定配置玩家當日首次取得翻牌機會時，系統依其標籤命中的模板決定當日的門檻表、獎項與權重，並連同 9 格排列一次鎖定。
當日不變鎖定後，當日內標籤變動、模板被編輯、活動被編輯，一律不影響已鎖定的玩家——飛行中的資料不被改寫。變更於該活動的次一個每日重置時點才生效。
未命中兜底未命中任何標籤規則（含新玩家、標籤資料尚未到位）→ 走預設配置，活動照常可玩。不得因無標籤而讓玩家看不到或無法參與活動。
可回溯須能事後查回「某玩家某日跑的是哪一檔活動、哪一版活動快照、哪一個模板的哪一版」，供客訴與對帳追溯。
三、每日重置行為
需求要達到的結果
觸發依各活動自行設定的每日重置時間點自動執行（時間一律以 UTC+8 設定與計算，線路不帶時區屬性）。不同活動可有不同重置時點，非全站統一。
清除當日累積押注、已解鎖／已翻開格狀態、當日 9 格排列與鎖定的配置。
保留歷史發放紀錄全數保留，供對帳與玩家查詢；重置不得影響任何已派彩紀錄。
邊界重置時點前後的押注須明確歸屬到正確的「活動日」，不得重複計入或漏計；重置執行本身須留下可查的執行紀錄（見 DEV §08）。
四、獎勵發放行為
需求要達到的結果
入帳形式現金獎一律經集成商以「Bet=0 / Win=獎項面額」的注單發放，直入平台主錢包真金、可立即提領；不分錢包別、不走促銷工具、不進紅利錢包。
先入帳後翻開須確認發放成功後才將格子標記為已翻開並向玩家顯示獎勵。不得先給畫面再補發獎。
失敗處理發放失敗時：格子維持未翻開、玩家不顯示獎勵、該筆派獎進入待處理狀態並自動重試至成功；同時須產生可被監控接住的失敗事件（見 DEV §15 警報）。
可對帳每筆派獎須留下足以對帳的收據：玩家、活動、獎勵類型、面額、發放時間、集成商端交易識別，並可與活動獎勵注單彼此勾稽。
五、重複發獎防護（同一格不可重複發獎）
硬性約束：同一玩家、同一活動、同一活動日、同一格子，最多只能產生一筆有效派獎。無論來源是玩家連點、網路重送、前端重試、後端重試或跨裝置同時操作，系統都必須只發一次。翻格請求須具備冪等性——重複的相同請求回傳與首次相同的結果，而不是再發一次獎。實作手段（唯一約束、鎖、去重鍵等）由開發決定。

六、斷線與重入的資料一致性
情境要達到的結果
翻格中途斷線若發放已成功但玩家未收到結果：重新進入時須看到該格已翻開並呈現實得獎勵，且不再發第二次。若發放未成功：該格維持未翻開、翻牌次數須還給玩家，玩家可重翻。不得出現「次數被扣掉但沒拿到獎」。
重入畫面玩家任何時候重新進入活動，畫面呈現的累積進度、可翻次數、已翻格與其獎勵都必須與後端狀態一致；後端為唯一真實來源，前端不得自行推算或快取覆寫。
多端同時開啟同一玩家在多個裝置／分頁同時開啟時，狀態須收斂為同一份；一端翻格後另一端不得仍可翻開同一格。
洗牌結果不可窺視未翻開格子的內容不得在翻開前傳給前端，避免玩家自行解出獎項分佈。
發放與紀錄同生共死「派獎成功」與「發放紀錄寫入」須一致——不可出現發了獎卻查無紀錄、或有紀錄卻沒入帳；任一側失敗都須可被對帳查出並補正。

整體美術風格基準

五、模板版本控制
2026-07-16 與後端 Eric 確認：模板既為可被多檔活動／多條規則共用的獨立實體，其編輯必須有版本控制，才不會在營運改一個模板時，連帶改掉正在運行的活動與玩家當日已鎖定的配置。
機制設計
模板編輯不換 ID同一模板 ID 下，每次儲存產生新版本序號（V1、V2…）。DB 已有序號，後台顯示時轉為版號格式（V1／V2）。活動引用的是模板 ID，不因編輯而斷開引用。
版本歷程每版保留完整快照（門檻／獎項／權重／各貨幣設定）。模板編輯器內重用活動 Tab 4 的模式呈現——版本下拉（格式「V1（更新 2026-06-28 10:12）」）＋該版快照明細。
生效時機· 模板被「運行中活動」引用時：新版本於各活動的「次一個每日重置時點」生效；玩家當日已鎖定的配置沿用舊版快照。
· 未被任何運行中活動引用的模板：儲存即生效。
· 此設計與 DEV §12 當日鎖定、DEV §13「飛行中資料不被改寫」同一設計哲學。

09 集成商發放需求（目的層級） INTEGRATION REQUIREMENTS
本章只列「需要集成商提供什麼能力」。對外的需求清單、參數與回傳格式由對接窗口另行維護，本文件不重複列出，也不指定介面形式。
一、現金獎發放（v1 啟用）
獎勵須經集成商以「Bet=0 / Win=獎項面額」之注單發放至平台主錢包，且可立即提領——不進紅利錢包、不走促銷工具、不附加流水條件。
需要的能力要達到的結果
注單可帶活動識別發放的注單須能帶上活動識別與獎勵類型，使活動獎勵可與一般遊戲注單分離辨識。
對帳可分離統計每日對帳報表中，活動獎勵須能與一般 GGR 獨立統計。
失敗可重試至成功派獎失敗須可持續重試至成功（比照既有免費遊戲的重試行為）；需確認是否有重試次數上限。
逐平台開通Bet=0 發放屬逐平台商務開通事項；未開通的線路不得被投放——後台可選線路清單只列已開通者（見 DEV §06）。
二、FREE SPIN 卡使用（v1 建好能力、v2 啟用）
需要的能力要達到的結果
可指定遊戲與注額發卡時須能指定可使用的遊戲與每轉注額（及局數、有效期限）。
可直接進入遊戲玩家使用卡片時，須能直接進入指定遊戲並自動套用該卡，中途不需玩家再次登入。
面額上限可控卡片贏分須能設定面額上限（max win）並確實生效。
結算與現金獎一致卡片結算所得同樣以 Bet=0/Win 注單入主錢包真金，並可歸回原卡片對帳。
使用紀錄可查發卡與使用紀錄須可查詢，供背包顯示與對帳使用。
時序原則：v1 與 v2 所需的集成商能力一次談齊、一次建好，避免分兩次介接造成重複的開發與等待。v2 不應再新增集成商介接工作。

本章依 2026/07 CRM 開案會議結論撰寫：定義「玩家標籤如何取得、如何比對到抽取門檻與獎項配置、標籤變動如何處理」。本章的 AND 複合標籤 → 單一配置 相對於 DEV §04「多 tag 依 DA Priority 取最高單一 tag」為準據，兩者並存時以本章為準；DEV §04 保留為技術背景與資料介面說明。
術語對齊：本章的「抽取門檻與獎項配置／設定檔」即 DEV §03／DEV §06 的「模板」（獨立實體、可被多檔活動與多條標籤規則共用）；「預設配置」＝後台固定置底、不可刪除、未命中任何規則時套用的模板（示範＝標準模板 A）。標籤僅用於選模板，無准入閘門。
一、標籤取得時機與匹配邏輯
項目設計
標籤取得時機玩家每日「登錄時」，由系統向數據組（DA）取得該玩家的多組 Tag（大/中/小客、風險標籤…）。非玩家每次動作即查，登錄時取一次當日快照。
匹配邏輯（核心變更）需同時符合多個標籤條件（AND 複合條件），才對應到該組抽取門檻與獎項配置。例：（大客 AND 非高風險） → 配置 A；（中客 AND 低風險） → 配置 B。單一標籤不足以命中，必須整組條件同時成立。
命中結果命中 → 套用該組「抽取門檻 + 獎項配置（9 格獎池／權重／目標 RTP）」；未命中任何一組 → 走預設配置（tag_default），活動仍可正常參與，不因未命中而消失。
重疊命中：玩家同時符合多條規則時採「符合度高者優先」——取標籤數最多且玩家全部符合的規則（見下方「五、防呆 · 衝突檢查」）。
資料來源一致性標籤值與分群定義由數據組提供，平台只接收 + 比對套用（非自動打標），沿用 DEV §04 B2 原則。
二、標籤變動處理（活動進行中不即時更換）
規則：活動進行中玩家標籤變動時，「不即時更換配置」；須待活動暫停更新後，玩家「下次登錄」才套用新標籤與新配置。
為何這樣設計（設計動機）：
  1. 避免影響進行中的活動：抽取門檻與獎項是「一整檔活動」的經濟模型參數，中途換配置會讓同一位玩家在同一檔活動裡出現「規則不一致」，破壞公平性與可預期性，也讓客訴與對帳難以歸因。
  2. 保護已累積進度：玩家當日／當檔已累積的押注進度與已解鎖翻牌次數，是依「命中當下的門檻」計算；即時換配置會使既有進度對不上新門檻，造成進度倒退或暴增的體感落差。
  3. 可控的切換點：把「換標籤」收斂到「活動暫停更新 → 下次登錄」這個明確切點，讓營運能預期何時生效、便於公告與風控，避免運行中資料在飛行中被改寫。
三、規則階段性與未來規劃
🟢 初期（本次範圍）
採「一層複合標籤規則」：多標籤組合 → 單一設定值，避免規則樹過於複雜。
標籤範圍先只做簡單分類：大客 / 中客 / 小客 ＋ 風險標籤。
🔮 未來規劃
導入分群模型，由模型輸出核心標籤供系統直接調用；
但保留規則兜底機制（rule fallback），確保模型異常或標籤缺失時活動仍可控可預期。

五、後台標籤設定（複選 ＋ 防呆友善介面）
UI 元件類型規則說明
標籤複選器Multi-select（Chips/Checkbox）後台設定標籤條件時須支援「複選」；標籤清單由數據組提供、後端直抓，不可自由輸入（沿用 DEV §04 B2）。已選標籤以 chip 呈現、可單獨移除。
複合條件群組AND 條件群組同一組配置的多個標籤以 AND 串接，介面明確標示「需同時符合」，避免誤解為 OR。初期僅一層（不做巢狀規則樹）。
防呆 · 衝突檢查即時驗證三層規則：
①「空規則」（未選任何標籤） → 紅底警示、擋送審（同原型 v2）。
②「標籤組合完全重複」（兩條規則的標籤集合完全相同） → 紅底警示、擋送審（同原型 v2）。
③「部分重疊」（一條規則的標籤是另一條的子集，玩家可能同時命中多條） → 合法、不擋；命中採「符合度高者優先」——取標籤數最多且玩家全部符合的那條規則。若同標籤數且同時命中多條 → 視為設定衝突，存檔時警示、擋送審。
防呆 · 預設兜底提示說明文字介面固定顯示「未命中任何組 → 走預設配置 tag_default」，提醒營運務必設好預設配置，避免玩家落空。
友善操作搜尋 / 分類 v2 標籤下拉支援搜尋與分類（客群類：大/中/小客；風險類：高/低風險）＋ hover 顯示標籤定義 → 列 v2；v1 標籤僅 5 個，以 chips 直選即可，不做搜尋與分類。
初期標籤範圍（本次僅做）：先只做簡單分類 —— 大客 / 中客 / 小客 ＋ 風險標籤；複雜分群與模型標籤列未來迭代。
13 後台管理與版本控制 ADMIN & VERSION CONTROL
本章依 2026/07 CRM 開案會議結論撰寫：定義活動列表、時區規範（UTC+8）、活動版本快照與流水號、活動複製、審核狀態機與角色權限矩陣。與 DEV §06 後台管理規劃互補（DEV §06 偏活動設定內容，本章偏版本控制與治理流程）。各種活動類型共用本章的審核流程與版本控制。
一、活動列表（可建立新活動）
欄位說明
活動名稱營運自訂。 名稱搜尋列 v2（v1 不提供搜尋；篩選以狀態 chips＋線路下拉＋日期區間為主）。
Campaign ID系統自動產生、唯讀（不可人工編輯），作為對帳與 audit 的唯一鍵。
活動類型該活動的玩法類型（v1 僅「抽寶箱」）。位於「版型」欄左側；篩選列另有活動類型下拉。建立活動時先選類型、表單內唯讀。詳見 DEV §06 活動類型擴充。
版型版型主題（theme_id，預定義單選；沿用 DEV §04／DEV §05 換皮架構）。
起訖時間活動開始 / 結束時間，一律以 UTC+8 設定與計算（見下）。
重置時間每日 reset 時間點（HH:MM），一律以 UTC+8（見下）。
適用線路投放的平台線路（chips 多選，取自預定義「已開通 Bet=0」清單）。
活動倒數即時倒數計時；剩餘天數 < 倒數啟動天數時轉紅。
狀態六態：草稿／送審中／已核准／運行中／已暫停／已結束（見審核狀態機）。移除「啟停」操作。
版本當前版本流水號（V1、V2…）。
操作查看 · 編輯 · 複製（移除 RTP／受眾 TAG 欄與啟停）。
篩選：活動類型下拉＋狀態 chips（含各狀態數量）＋線路下拉＋日期區間＋清除篩選。活動複製：複本帶入全部設定、狀態重置為草稿、版本 V1、ID 加 _COPY。
二、時區處理
系統唯一時區＝UTC+8：活動起訖時間、每日重置時間，一律以 UTC+8 設定、顯示與計算（前端、後端、DB、排程皆同）。
線路不帶時區屬性：投放線路僅代表站台／地區，不參與任何時間計算。
營運換算原則：跨時區線路（如泰國、越南）的當地生效時間，由營運人員於建立活動時自行換算成 UTC+8 填入（例：希望泰國當地 00:00 重置 → 填 01:00）。
＊設計理由：不做線路時區動態計算——單一時區可消除跨線路「當日」定義的工程複雜度與排程邊界案例，換算成本移轉給營運端，屬可接受的人工成本。
三、版本編輯與存檔（快照 ＋ 流水號）
機制設計
運行期間可編輯活動運行期間可編輯；系統以「快照（snapshot）」保留正在運行的規則，不影響已參與玩家（進行中玩家沿用命中當下的快照）。
版本流水號每次編輯自動產生版本流水號（V1、V2…）。
運行中 vs 待生效
UI 呈現		資料層保留「運行中版本（current）」與「待生效版本（pending）」；編輯產生的是待生效版本，於下一個生效切點（活動暫停更新 / 排程）才切換為運行中。UI 不顯示「運行中/待生效」badge，改以活動表單 Tab 4「版本下拉＋快照明細」呈現（下拉選項格式「V1（更新 2026-06-28 10:12）」）。
多版本並存同一活動不同版本可並存，支援比對與追溯（誰在何時改了什麼、玩家當時跑哪一版）。
快照計數規則快照明細的「標籤規則數量」＝規則 N 組，預設配置另列、不計入 N；顯示格式「N 組規則 ＋ 預設」。⚠ N 不含預設配置，文案須寫「N 組規則 ＋ 預設」。
引用模板版本活動版本快照引用「模板 ID ＋ 模板版本序號」（非僅模板 ID），確保回溯時取得的是當時實際生效的那一版模板數值；活動 Tab 4 快照明細中的模板名稱須帶版號（例：忠誠加碼 V2）。模板版本控制機制見 DEV §06 五、模板版本控制。
與標籤變動一致此「快照 + 下次切點生效」機制與 DEV §12「標籤變動不即時、待暫停更新後下次登錄套用」同一設計哲學：飛行中資料不被改寫。
四、活動複製功能
活動複製：可將現有活動複製為新活動——複本帶入全部設定、狀態重置為草稿、版本 V1、ID 加 _COPY（新活動取得全新 Campaign ID·唯讀），加速同型活動開檔、降低重填錯誤。
五、審核流程（狀態機 · 六態）
規則：設定完成後提交審查，由最高權限（Admin）核准後方可上線；一般操作者不可自審自上（職責分離）。活動狀態六態：草稿 → 送審中 → 已核准 → 運行中 → 已暫停 → 已結束；駁回 → 回草稿並顯示駁回原因（必填）。上線中 ⇄ 已暫停 可互切（緊急調整先暫停）。
暫停／恢復的操作入口（明定）：運行中 ⇄ 已暫停 的操作入口＝活動表單（查看／編輯頁）頂部狀態列的「暫停活動／恢復活動」按鈕，僅最高權限（Admin）可操作。活動列表不提供啟停（不提供一鍵啟停）。

14 獎勵發放與數據原則 REWARD PAYOUT & DATA PRINCIPLES
本章只列必須成立的原則。資料流拓撲、佇列選型、同步頻率與串接方式由開發自行決定，只要下列原則與驗收標準成立即可。
一、Bet=0 發放
活動獎勵一律經集成商以「Bet=0 / Win=獎項面額」的注單發放，直入平台主錢包真金、可立即提領。不分錢包別、不進紅利錢包、不附流水條件。
約束：Bet=0 屬逐平台開通事項，未開通的線路不得被投放（後台可選線路清單只列已開通者）。
二、RTP −1% 守恆原則
活動預算來自將相關線路或標籤玩家的 RTP 調降 1%——這是「挪移」而非「加碼」：「遊戲內 RTP（X−1）% ＋ 活動獎勵 1%」＝原 X%，整體 RTP 佔比不提升，對帳須可驗證兩者相加守恆。
三、獎勵歷程可查性
原則要達到的結果
獨立於遊戲歷程活動獎勵（現金、FREE SPIN 卡等）須獨立成一套可查的獎勵紀錄，與遊戲內派彩歷程分離。
營運查得到營運端於遊戲後台「資料查詢 → 投注資料查詢」以「注單類型＝活動獎勵」即可查得，並額外看到 CAMPAIGN ID 與獎勵類型（見 DEV §06）。不另設 CRM 獨立查詢頁。
玩家查得到玩家端於遊戲歷程「活動」入口可查自己的全部抽寶箱獎勵歷程（見 DEV §05）；與營運端同源一致。
可分類紀錄須能區分活動類型（抽寶箱／未來其他玩法）與獎勵類型（現金／FREE SPIN 卡），供分類統計。
可回溯到版本每筆紀錄須能追回命中的活動版本與模板版本，回答「玩家當日跑的是哪一版設定」。
四、GGR 歸屬原則
活動獎勵不計入單一遊戲 GGR。玩家可跨遊戲累積押注並參與活動，獎勵若被歸入任一款遊戲，會造成該遊戲收益失真。此原則不因查詢頁整併至投注資料查詢而改變——同一頁查得到，不代表可併入該遊戲的收入口徑。
五、標籤資料供給的行為要求
需求要達到的結果
批次即可、不需即時標籤資料以定期批次供給即可，不需即時查詢；隔日生效可接受。傳輸方式由開發決定。
供給中斷不擋活動標籤資料延遲或缺漏時，玩家走預設配置、活動照常可玩；不得因此讓玩家看不到活動或無法領獎。
不做無效同步無任何活動可參與的玩家不需納入同步範圍，避免無效資料量。
可查當日快照須能查回「某玩家某日的標籤為何、因此命中哪條規則、用了哪個模板」。

什麼情況通知誰為什麼要立刻知道
派獎失敗且重試後仍未成功值班工程 ＋ 營運玩家獎勵懸空，需人工補救；持續失敗代表發放通道有問題。

每日重置排程未在預定時點執行值班工程玩家當日進度不會歸零，活動邏輯全盤失準。
單日活動獎勵發放總額超出預期區間營運 ＋ 數據組成本失控的第一個訊號，需即時判斷是否暫停活動。
標籤資料供給中斷或大量缺漏值班工程 ＋ 數據組玩家會大量落入預設配置，分眾投放形同失效。
實際 RTP 明顯偏離模板目標值數據組 ＋ 營運代表權重設定或發放邏輯有誤，直接影響成本與合規。
